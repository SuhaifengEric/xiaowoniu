## 需求摘要

### 问题陈述

Phase 8 已证明功能在本地数据库和真实浏览器中可用，但尚未形成目标环境的配置、构建、部署、迁移、备份恢复、监控告警和回滚闭环。直接进入生产会把运行风险转嫁给首批用户。

### 范围

本阶段包含：

1. 发布责任、目标环境和部署方式的决策记录。
2. 可重复执行的 CI 质量门禁与构建产物追溯。
3. Staging 的前端、后端、PostgreSQL 配置、部署和健康检查。
4. Prisma migration 的审批、备份、恢复演练和回滚准则。
5. 日志脱敏、请求追踪、关键接口与数据库运行指标。
6. Staging 上的真实 HTTP 冒烟和浏览器验收。
7. 生产发布审批、观察窗口和回滚运行手册。

明确不在范围内：

- 新的 Fitness、Learning、Finance、Wedding 业务功能。
- 未经数据证据的 Dashboard 缓存层、实时推送或数据仓库。
- 未经评估的 React Router v7 升级。
- 在本计划批准前执行生产部署、`prisma migrate deploy` 或写入任何生产密钥。
- 假设某个云厂商、容器平台、域名、告警工具或备份产品已经可用。

### 成功标准

- [ ] 任何 Staging 发布都可追溯到唯一的审查通过提交 SHA、依赖锁文件和构建产物。
- [ ] CI 在干净环境中执行 `pnpm install --frozen-lockfile` 与 `pnpm verify`，失败时阻止构建产物进入发布流程。
- [ ] Staging 的后端、前端和 PostgreSQL 使用受管环境变量；仓库、构建日志和计划文档中不出现真实密钥。
- [ ] Staging migration 仅在备份、变更窗口和负责人确认后执行，并记录前后 migration 状态。
- [ ] 备份可以在隔离数据库中恢复，并完成 Finance、Learning、Wedding、Dashboard 关键数据的抽样核对。
- [ ] Staging 提供 liveness 与数据库 readiness 检查；部署后能定位版本、请求失败和数据库异常。
- [ ] 真实浏览器在 Staging 完成登录、Dashboard、四模块快捷入口、写入、删除确认、隔离和错误重试的冒烟验收。
- [ ] 生产发布复用已在 Staging 验证的同一构建产物，并有明确的放行、观察和回滚条件。

### 约束

- 继续使用 Node.js 20+、pnpm 8+、Express、Prisma、PostgreSQL 15+、React/Vite 现有技术栈；不为发布阶段新增第二套业务运行时。
- 后端现有关键环境变量为 `DATABASE_URL`、`JWT_SECRET`、`JWT_EXPIRES_IN`、`PORT`、`NODE_ENV`、`FRONTEND_URL`、`LOG_LEVEL`；前端使用构建期 `VITE_API_URL`。
- 生产数据库迁移必须由目标环境的受权凭据执行；本地临时 `DATABASE_URL` 覆盖不能复用为生产做法。
- 任何恢复演练必须使用隔离数据库或经脱敏的数据，不复制或泄露真实用户数据。

### 需先确认的决策

| 决策 | 需要确认的内容 | 未确认时的处理 |
|---|---|---|
| 托管方式 | 目标云/主机、是否容器化、反向代理、域名与 TLS 责任边界 | 停留在发布设计与本地验证，不制作带平台假设的部署脚本。 |
| Staging 数据 | 空库、合成数据或脱敏副本；保留周期和访问权限 | 默认使用空库与合成验收数据。 |
| 密钥管理 | 部署平台 Secret、Vault 或其他受管方案；轮换负责人 | 不在仓库创建真实 `.env` 或复制生产连接串。 |
| 备份目标 | RPO、RTO、保留期、恢复负责人和存储位置 | 不执行任何目标环境 migration。 |
| 运行观测 | 日志、指标、告警渠道及观察人 | 先保留结构化日志与最小指标接口设计，不接入未批准的第三方。 |
| 发布治理 | 发布负责人、审批人、观察窗口、回滚授权人 | 不进入生产放行步骤。 |

## 架构与发布流

### 采用方式

采用“同一构建产物逐级提升”的受控发布流，而不是从开发机或不同分支分别构建 Staging 和生产。

```mermaid
flowchart LR
  A["审查通过的提交 SHA"] --> B["CI: frozen lockfile + pnpm verify"]
  B --> C["带 SHA 的不可变构建产物"]
  C --> D["Staging 配置与部署"]
  D --> E["备份确认 → prisma migrate deploy → readiness"]
  E --> F["Ego 浏览器冒烟与观察"]
  F --> G{"发布审批"}
  G -->|"批准"| H["复用同一产物生产发布"]
  G -->|"拒绝或异常"| I["停止提升 / 执行回滚手册"]
```

### 关键组成

- **发布清单：** 记录提交 SHA、构建时间、依赖锁文件摘要、迁移目录、环境、审批人与构建产物位置。
- **CI 质量门禁：** 使用根目录现有 `pnpm verify`，补充 frozen lockfile 安装、测试报告和构建产物保存；CI 不连接生产数据库、不运行 `prisma migrate deploy`。
- **环境配置层：** 由部署平台注入后端 Secret 和前端 `VITE_API_URL`；构建前明确前端 API 地址，避免将本地地址打进 Staging 产物。
- **运行检查：** 保留现有 `/health` 作为存活检查；新增或明确 `/readyz` 用于数据库连接与必要依赖就绪判断，避免仅凭进程存活判定可接流量。
- **数据库变更门：** 迁移评审、备份成功、恢复演练、变更窗口和负责人齐备后，才允许目标环境执行 `prisma migrate deploy`。
- **运行观测：** 在现有 Winston 请求/错误日志基础上，增加生产可查询的 JSON 日志、脱敏、请求关联 ID、版本标识及关键运行指标。

### 数据与控制流

1. 开发完成后，审查者确认变更无真实密钥、无未授权删除，并形成可发布提交。
2. CI 从该提交安装锁定依赖、执行质量门禁、生成前后端构建产物并记录 SHA。
3. Staging 用该产物及 Staging Secret 启动；完成 `/health`、`/readyz`、CORS、版本和数据库连接检查。
4. 负责人确认备份和恢复演练证据后，在 Staging 执行 migration；失败时停止部署并按恢复手册处理。
5. 使用 Staging 测试账号做真实浏览器验收；监控日志、错误率、Dashboard 聚合延迟和数据库健康。
6. 只有 Staging 通过且审批完成时，才将同一产物提升到生产；生产不重新从工作树构建。

## 实施计划

### 阶段 0：发布决策与责任边界

**动作：**

- 确认 Staging/生产的托管平台、网络入口、域名/TLS、进程或容器运行方式、PostgreSQL 责任边界。
- 明确发布负责人、数据库负责人、备份恢复负责人、观察人和回滚授权人。
- 创建 `docs/ops/phase9-deployment-decision-record.md`，仅记录非敏感决定与责任分工；真实密钥只存部署平台。
- 确认 Staging 使用空库与合成数据，还是经审批的脱敏数据；定义访问权限和销毁规则。

**交付物：** 部署决策记录、责任人矩阵、Staging 数据策略。

**退出条件：** 不再依赖“假设某云平台可用”；后续部署文件可以针对已批准的目标实现。

### 阶段 1：清理发布基线与代码审查

**动作：**

- 审查当前 Phase 8 改动，区分业务源码、测试、文档和工具缓存；禁止把 `.pnpm-store/`、`.reasonix/`、`.zcode/` 等本地缓存带入发布提交。
- 执行 `git diff --check`、密钥扫描和依赖锁文件核对；确认 Dashboard 聚合继续直接使用 Prisma，而非内部 HTTP 调用。
- 在用户批准后，将相关改动整理为可审查提交并更新版本/变更日志；本计划不自行提交或推送。
- 生成发布清单模板，至少包含提交 SHA、版本、构建编号、迁移名称、审批记录和回滚提交。

**交付物：** 审查记录、干净的发布基线、发布清单模板。

**依赖：** 阶段 0 的负责人和发布治理已明确。

### 阶段 2：建立 CI 质量门禁与构建产物

**动作：**

- 在已选定的 CI 平台创建工作流：`pnpm install --frozen-lockfile` → `pnpm verify` → 保存测试结果与前后端构建产物。
- 让 CI 使用 Node.js 20+、pnpm 8+ 和锁定依赖；失败日志必须保留，不使用 `|| true` 吞错。
- 为构建产物写入提交 SHA 和构建时间；前端按目标环境注入 `VITE_API_URL`。
- 将 migration 检查限制为 `prisma validate`、`prisma generate` 和迁移目录变更审阅；不在 CI 中自动对任何共享数据库执行 deploy。

**交付物：** CI 工作流、构建产物保留策略、发布清单自动填充字段。

**验收：** 从干净 checkout 运行一次，能重现本地 `pnpm verify` 的通过/失败结果。

### 阶段 3：配置 Staging 运行环境

**动作：**

- 根据阶段 0 的平台决策创建后端、前端和 PostgreSQL 的 Staging 配置；配置 `NODE_ENV=staging`、`FRONTEND_URL`、`VITE_API_URL` 和受管 Secret。
- 保持后端的 `SIGTERM` 优雅关闭；检查反向代理超时、CORS、TLS 终止与静态前端路由回退是否符合已选平台。
- 将现有 `/health` 定义为 liveness；新增或完善 `/readyz`，使其仅在 Prisma/数据库可连接时返回 ready，并避免在响应中输出连接串或内部异常。
- 提供非敏感版本信息端点或响应头，供观察人与问题定位使用。

**交付物：** 平台相关的 Staging 部署说明/清单、环境变量清单、liveness/readiness 契约。

**验收：** 未注入 Secret 时服务安全失败；注入正确 Staging 配置后，前后端可访问、`/health` 与 `/readyz` 语义正确。

### 阶段 4：数据库迁移、备份与恢复闭环

**动作：**

- 审阅所有 migration 的顺序、数据影响和向后兼容性，尤其是 Finance、Learning、Wedding、Dashboard 相关表。
- 在 Staging migration 前生成可验证的 PostgreSQL 备份，记录时间、数据库标识、校验结果、保留期和负责人；备份文件不得写入仓库。
- 在隔离数据库执行恢复演练，核对用户隔离、考试/科目/打卡、消费/预算、备婚任务/花费和 Dashboard 摘要的关键样本。
- 将 `prisma migrate deploy` 放入有负责人确认的运行手册：备份成功 → 迁移状态记录 → deploy → `/readyz` → 冒烟；任一步失败即停止提升。
- 定义回滚策略：应用回退优先复用已验证构建；数据库只在恢复演练确认后恢复，禁止临场假设“向下迁移”可用。

**交付物：** migration 审查记录、备份/恢复演练记录、数据库发布与回滚运行手册。

**验收：** 完成至少一次隔离恢复演练；负责人能依据手册复现恢复步骤和验收结果。

### 阶段 5：最小可观测性与日志安全

**动作：**

- 将生产日志稳定为可检索的 JSON；移除仅适合本地终端的颜色格式，保持 timestamp、level、服务版本、环境和请求关联 ID。
- 定义脱敏清单：`Authorization`、JWT、密码、`DATABASE_URL`、Cookie、完整请求体和个人敏感字段不得写入日志。
- 为请求日志增加 method、路由模板、状态码、耗时和 request ID；错误日志关联 request ID，但不把堆栈直接返回给客户端。
- 建立最小运行指标：后端 5xx、请求量、p50/p95 延迟、数据库连接/查询异常；Dashboard 聚合端点单独记录延迟和失败率。
- 为指标定义初始观察阈值与联系人；阈值先用于观察，不在没有基线时承诺不合理的 SLO。

**交付物：** 日志字段与脱敏规范、指标清单、告警路由说明、Dashboard 运行看板需求。

**验收：** 在 Staging 人为触发一次安全的失败请求后，可从 request ID 定位错误，且日志中不含 Secret 或敏感字段。

### 阶段 6：受控 Staging 发布与真实验收

**动作：**

- 使用阶段 2 的唯一构建产物进行 Staging 部署；记录部署开始/结束时间、提交 SHA、环境和操作者。
- 按阶段 4 手册执行备份确认、migration 和 ready 检查。
- 以 Staging 临时隔离账号执行真实 HTTP 冒烟；需要浏览器操作时使用 Ego 浏览器。
- 浏览器验收至少覆盖：注册/登录、Dashboard 四模块摘要、Fitness/Learning/Finance/Wedding 快捷入口、创建一条可清理数据、删除确认、用户隔离、错误重试和登出。
- 观察日志、错误率、Dashboard 聚合延迟和数据库健康；发现阻塞问题则停止提升并形成缺陷记录。

**交付物：** Staging 发布记录、浏览器验收记录、监控快照、已知问题列表。

**验收：** 全部 Phase 8 手工验收关键路径在 Staging 通过，且无未解释的服务端错误或数据串户迹象。

### 阶段 7：生产发布准备与受控提升

**动作：**

- 召开发布评审，核对阶段 0–6 的交付物、未解决风险、回滚责任人、观察窗口和用户影响说明。
- 仅在审批通过后，使用同一 SHA/构建产物、生产 Secret 和经确认的迁移运行手册发布。
- 发布后执行最小生产冒烟，不使用真实用户数据做破坏性操作；观察窗口内关注错误率、认证失败、Dashboard 聚合、数据库连接与迁移异常。
- 明确停止/回滚阈值：认证或核心写入不可用、数据隔离疑点、迁移异常、持续 5xx、关键延迟显著劣化均应停止继续放量。

**交付物：** 生产发布审批单、发布记录、观察记录、回滚结论。

**依赖：** 阶段 0–6 全部完成，且用户明确授权生产发布。

### 阶段 8：持续交付与技术债务排序

**动作：**

- 把 CI、迁移审查、Staging 冒烟和发布清单固化为每次发布的必经门禁。
- 基于 Staging/生产数据评估 Dashboard 聚合索引与缓存需求；只有查询证据表明确实需要时才设计缓存。
- 评估 React Router v7 future flags；先在独立分支与 CI 验证，避免与发布保障工作混合。
- 定期演练恢复、轮换 Secret、复审日志脱敏和告警阈值。

**交付物：** 发布节奏清单、运维改进 backlog、定期演练记录。

## 技术注意事项

- `pnpm verify` 的 Prisma validate/generate 不会连接并验证目标数据库迁移；目标环境状态必须通过独立的 `prisma migrate status` 和受控的 `prisma migrate deploy` 确认。
- Vite 的 `VITE_API_URL` 是构建期配置；构建产物提升前必须确认 API 地址，不应依赖部署后临时修改源文件。
- 现有 `/health` 适合作为进程存活信号，但不能取代 readiness；数据库不可用时，服务不应被负载均衡继续接入。
- 现有日志已包含 Winston、请求耗时和错误记录；Phase 9 应增强而非替换，重点是 JSON 一致性、request ID 和脱敏。
- Prisma migration 的安全回滚通常不是自动“down migration”；计划以向前兼容、经过恢复验证的备份和应用版本回退为准。
- Staging 与生产应使用不同数据库、不同 Secret、不同测试用户和明确的网络边界；禁止把本地或 Staging 的数据库连接串复制到文档或代码。

## 风险管理

| 风险 | 影响 | 概率 | 缓解措施 |
|---|---|---|---|
| 从脏工作树或未经审查的改动发布 | 高 | 高 | 阶段 1 形成干净提交与 SHA 发布清单；CI 只从该 SHA 构建。 |
| 托管平台与网络方案未定 | 高 | 高 | 阶段 0 为硬门禁；不预先编写绑定某平台的部署脚本。 |
| migration 或恢复失败造成数据不可用 | 高 | 中 | 迁移前备份、隔离恢复演练、变更窗口、负责人确认和停止规则。 |
| 日志泄露 JWT、连接串或个人数据 | 高 | 中 | 字段白名单、统一脱敏、生产 JSON 日志审查和安全失败测试。 |
| Staging 与生产构建不一致 | 高 | 中 | 使用不可变产物与相同 SHA 提升；禁止生产重新从工作树构建。 |
| Dashboard 聚合在真实数据量下延迟升高 | 中 | 中 | 先记录延迟/失败率和数据库指标，再基于证据做索引或缓存决策。 |
| 无负责人或无观察窗口导致异常无人处理 | 高 | 中 | 发布审批单必须列出责任人、通知渠道、观察时段和回滚授权。 |
| Staging 使用真实数据但缺乏脱敏 | 高 | 低至中 | 默认合成数据；改用副本前需完成脱敏、访问控制和保留期审批。 |

## 附录：澄清摘要与备选方案

### 规划假设与缺口

- 假设：Phase 9 首先建立 Staging，再决定是否发布生产；不把生产发布视为已获授权。
- 假设：Staging 默认使用合成测试数据；任何真实数据副本均需独立审批。
- 缺口：目标平台、域名/TLS、Secret 管理、备份产品、监控产品、RPO/RTO 和发布责任人未指定。
- 缺口：目前无 CI 与部署文件；阶段 0 的决策将决定后续实现文件，而非反向由计划臆造平台。

### 备选方案

| 方案 | 结论 | 原因 |
|---|---|---|
| 直接从本地发布生产 | 不采用 | 无不可变构建、无恢复演练、无 Staging 证据，风险不可接受。 |
| 先完成 Staging 再提升生产 | 采用 | 可在隔离环境验证配置、迁移、浏览器路径和观察能力。 |
| 立即引入缓存层 | 暂缓 | Phase 8 Dashboard 当前以直接 Prisma 聚合为权威；需先有真实延迟和查询证据。 |
| 立即升级 React Router v7 | 暂缓 | 属于可选技术债务，应在独立分支和 CI 中验证，不与发布保障混合。 |
