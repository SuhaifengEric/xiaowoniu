# 嫁嫁嫁模块业务需求

> 版本：v0.2
>
> 日期：2026-08-13
>
> 定位：以男女双方和双方家庭真实交往为主线的婚姻进程记录与推进工作台。

## 1. 产品判断

“嫁嫁嫁”不是一张备婚任务清单，也不是父母审批系统。它要帮助两个人记录并推进一段真实的婚姻过程：

> 两人确认婚姻意愿 → 两次上门见家长（先后可调，但都要完成） → 双方父母见面 → 形成婚姻基本共识 → 订婚（可选） → 双方自主安排领证与婚礼顺序 → 领证与婚礼分别完成 → 进入婚后生活。

这条流程是常见场景下的推荐主线，不是法律规定，也不是所有家庭必须遵循的唯一顺序。用户可以调整尚未发生节点的顺序、日期和推进方式；系统不能把习俗、父母意见或日期安排伪装成法律结论。

## 2. 用户与角色

### 2.1 主要用户

- 男女双方中的任一方，作为主要记录人和推进人。
- 记录对象是两个人共同的婚姻进程，而不是单独一方的待办事项。

### 2.2 参与角色

| 角色 | 在真实场景中的作用 | 系统中的边界 |
| --- | --- | --- |
| 男女双方 | 是否结婚、何时推进、采用什么顺序的最终决策主体 | 可以创建、调整和完成节点；可以记录双方共识 |
| 男方家庭 | 接待女方上门，参与父母见面和婚事讨论 | 作为参与人/备注被记录，不需要独立账号 |
| 女方家庭 | 接待男方上门，参与父母见面和婚事讨论 | 作为参与人/备注被记录，不需要独立账号 |
| 双方父母 | 表达意见、了解彼此家庭、参与约定 | 不是系统中的审批人；意见不自动等于流程通过 |
| 亲友/供应商 | 可能参与婚礼执行 | 一期不作为独立业务角色 |

一期采用当前小窝牛的个人账户模型：数据归当前用户所有，不做情侣双账号、父母账号或多人协作权限。页面文案应使用“共同决定”“记录双方共识”，避免让单个用户误解为系统可以替双方作决定。

## 3. 真实业务流程

### 3.1 主流程

| 阶段 | 真实场景 | 进入条件 | 完成标志 | 可回退/异常 |
| --- | --- | --- | --- | --- |
| 01 两人确认意愿 | 两个人决定以结婚为目标，愿意让双方家庭正式认识 | 双方已经讨论过婚姻意愿 | 双方愿意进入家庭接触 | 任一方尚未确定时，停留在两人沟通 |
| 02 安排两次上门 | 双方决定谁先上门、分别安排时间 | 阶段 01 已记录或用户补录 | 明确“男方先”或“女方先” | 尚未发生的顺序可以调整 |
| 02A 男方上门 | 男方到女方家正式拜访、表达婚姻意愿 | 已安排时间或用户补录 | 拜访实际完成并留下结果 | 未完成可以改期、暂缓或重新安排 |
| 02B 女方上门 | 女方到男方家正式拜访、认识家庭 | 已安排时间或用户补录 | 拜访实际完成并留下结果 | 未完成可以改期、暂缓或重新安排 |
| 03 双方父母见面 | 双方父母第一次面对面谈婚事和家庭相处方式 | 02A、02B 都完成 | 见面完成，并记录主要结论 | 意见不一致时标记“需再沟通”，不能强行通过 |
| 04 基本共识 | 两个人与双方家庭讨论婚姻方向 | 阶段 03 已完成或用户补录 | 关键议题形成可执行共识 | 任何议题未解决都可以暂停订婚 |
| 05 订婚 | 按双方和当地习俗完成订婚、礼节或承诺约定 | 阶段 04 有足够共识 | 订婚完成，或明确记录为跳过 | 订婚是可选节点，不等于领证 |
| 06 安排顺序 | 两个人决定领证和婚礼的先后及日期 | 阶段 04 已有方向；订婚可完成、进行中或跳过 | 明确一种顺序方案 | 尚未发生的节点可以重新排序和改期 |
| 07A 领证 | 两人依法办理结婚登记 | 双方决定进入法律婚姻 | 记录真实领证日期 | 未领证前不显示“已依法结婚” |
| 07B 婚礼 | 完成婚礼、宴请或双方约定的结婚仪式 | 双方确定仪式方案 | 婚礼实际完成 | 婚礼延期不等于关系失败；已领证不必等待婚礼才成立婚姻 |
| 08 婚姻阶段完成 | 领证与婚礼两个节点都完成 | 07A、07B 均完成 | 进入婚后生活/归档 | 只完成一个时，另一个保持进行中 |

### 3.2 两个必须由用户控制的顺序

#### 两次上门顺序

可选值：

- 男方先上门，女方后上门
- 女方先上门，男方后上门

这是“顺序可调”，不是“二选一”。两次上门都必须拥有独立记录，且只有两次都完成后，父母见面才成为推荐的下一步。

#### 领证与婚礼顺序

可选值：

- 先领证，后办婚礼
- 先办婚礼，后领证
- 同日或临近日期完成

领证和婚礼必须是两个独立节点，分别维护计划日期、实际日期、状态和备注。改变顺序只影响未来计划，不改写已经发生的事实。

## 4. 核心场景需求

需求从用户正在经历的场景出发，而不是从页面菜单出发。

| 场景 | 用户目的 | 当前行动 | 系统需要记录 | 完成标准 |
| --- | --- | --- | --- | --- |
| 两人准备见家长 | 把恋爱关系正式带入家庭 | 商量谁先上门、什么时候去、带什么、怎么介绍 | 上门顺序、计划日期、参与人、准备事项 | 两次上门顺序清楚，至少下一次有日期和行动 |
| 一次上门结束 | 知道家庭是否已认识并接受这段关系 | 记录见面结果、顾虑和下一步 | 实际日期、参与人、结果、待处理问题 | 该次拜访明确标记完成，未解决问题保留 |
| 两家父母见面 | 让两个家庭开始面对面谈婚事 | 安排见面并记录谈话结论 | 见面日期、参与人、主要共识、分歧 | 不是“父母同意”才算完成，而是见面真实发生且结论可追溯 |
| 讨论婚姻共识 | 避免只谈仪式、不谈婚后生活 | 逐项讨论城市、时间、费用、责任等 | 议题状态、双方结论、待沟通项 | 关键议题有明确“已共识/待沟通”状态 |
| 订婚或跳过订婚 | 按习俗完成承诺，或明确不采用该节点 | 记录订婚安排或跳过原因 | 是否采用、日期、礼节、费用边界、备注 | 完成或明确跳过，不留下无法解释的“未完成” |
| 决定先领证还是先办婚礼 | 把法律节点和仪式节点安排成适合自己的顺序 | 选择顺序、定日期、调整计划 | 顺序方案、两个节点的计划/实际日期 | 两个节点都可独立推进，不能被系统锁死 |
| 婚礼筹备 | 把仪式约定落实为具体执行 | 场地、礼服、摄影、宾客等准备 | 阶段任务、预算、花费、供应商备注 | 关键事项完成或有明确替代方案 |
| 婚姻阶段复盘 | 知道现在卡在哪里、下一步是什么 | 查看阶段、风险和待办 | 当前阶段、逾期、待沟通、预算差额 | 用户打开页面即可知道下一步行动 |

## 5. 信息架构与页面原型基线

原型不按“任务/花费/预算”作为一级业务入口，而按婚姻阶段组织信息。

### 5.1 页面层级

1. **婚姻进程首页**：当前阶段、下一步、主流程进度、两个可调顺序、风险提醒。
2. **阶段详情**：某个真实场景的日期、参与人、结论、待办和历史记录。
3. **共识记录**：关键议题逐项标记“已达成共识/需再讨论/尚未讨论”。
4. **婚礼执行**：婚礼相关任务、预算、计划花费、实际花费和支付状态。
5. **流程设置**：调整两次上门顺序、调整领证/婚礼顺序、补录已完成节点。

### 5.2 首页必须回答的问题

- 我们现在处于哪个真实阶段？
- 下一步由谁、在什么时候、做什么？
- 两次上门分别是什么状态，顺序是什么？
- 双方父母见面和基本共识是否已经记录？
- 领证和婚礼采用什么顺序，两个日期分别是什么？
- 当前有哪些需要重新沟通的事项？
- 婚礼预算是否需要调整？

## 6. 功能需求

### REQ-MAR-001 建立婚姻进程

- 用户可以创建一个婚姻进程，也可以选择从任意已发生阶段开始补录。
- 首次进入不能强迫用户从“确认意愿”重新开始；现实中已经见过家长或已订婚的用户可以直接补录当前状态。
- 用户可以标记自己是男方、女方或记录人；该信息只用于页面称呼和默认提示，不决定谁拥有婚姻决策权。

### REQ-MAR-002 阶段状态

每个节点支持：`未开始`、`已安排`、`进行中`、`已完成`、`暂缓`。订婚额外支持 `已跳过`。

- 完成必须由用户明确操作或补录，系统不能仅凭计划日期自动完成。
- 完成记录至少包括实际日期；可选包括参与人、结论、备注和证据链接/附件（附件可后置）。
- 状态变更保留更新时间；重新打开已完成节点时不能删除历史完成日期，需明确改为“进行中”后再编辑。

### REQ-MAR-003 两次上门顺序控制

- 用户可以在流程设置中选择“男方先”或“女方先”。
- 两个上门节点必须分别展示、分别记录、分别完成。
- 只完成一次时，首页明确显示“还差另一方上门”，不显示“父母见面可进行”以外的虚假完成状态。
- 尚未发生的节点允许调序；已经完成的上门记录不因调序而被改写。

### REQ-MAR-004 双方父母见面

- 只有两次上门都完成后，系统才把双方父母见面显示为推荐下一步；用户仍可以补录现实中已经发生的见面。
- 记录见面日期、参与人、主要结论、分歧和下一步。
- 文案使用“见面已记录/需要再沟通”，不使用“父母审批通过”。

### REQ-MAR-005 婚姻基本共识

提供默认议题，但允许用户增删或改名：

- 是否确定进入婚姻
- 婚后居住城市/居住安排
- 领证与婚礼时间
- 婚礼规模和双方家庭参与方式
- 费用、礼金和预算边界
- 婚后家庭责任和重要生活安排

每个议题支持：`尚未讨论`、`讨论中`、`已达成共识`、`需再沟通`。系统展示未解决议题，但不自动判断对错，也不阻止用户进入下一阶段。

### REQ-MAR-006 订婚节点

- 用户可以选择采用订婚、跳过订婚或暂不决定。
- 采用订婚时记录计划日期、实际日期、礼节/仪式、费用边界和备注。
- 跳过时记录“跳过原因”可选；跳过后不进入异常提醒，也不计算为未完成任务。

### REQ-MAR-007 领证与婚礼顺序控制

- 用户可选择“先领证后婚礼”“先婚礼后领证”“同日/临近完成”。
- 领证节点和婚礼节点独立维护：状态、计划日期、实际日期、备注、相关行动项各自独立。
- 用户可以调整尚未完成节点的顺序和日期。
- 已完成节点的实际日期是事实记录，不因后续调整而改变。
- 只有领证和婚礼均完成时，首页才显示“婚姻阶段已完成”。

### REQ-MAR-008 阶段行动项

行动项必须挂在具体阶段下面，不再以脱离场景的通用任务作为首页主结构。

行动项字段：名称、所属阶段、负责人（男方/女方/双方/家庭）、计划日期、状态、完成标准、备注。

示例：

- “确定女方上门日期” → 两次上门
- “准备双方父母见面要讨论的问题” → 父母见面
- “确认婚后居住城市” → 基本共识
- “预约结婚登记” → 领证
- “确认婚宴场地和档期” → 婚礼

### REQ-MAR-009 婚礼预算与花费

- 预算和花费属于婚礼执行阶段的支撑信息，不应取代婚姻关系主流程。
- 保留预计金额、确认金额/实际金额、支付状态和备注。
- 页面必须明确“确认金额”不等于“已经支付金额”。
- 花费可以关联具体行动项，也可以独立存在；删除行动项不能删除历史花费。
- 预算超支只产生风险提示，不自动修改流程阶段或替用户取消事项。

### REQ-MAR-010 首页复盘

首页按优先级展示：

1. 当前阶段与阶段完成度
2. 下一步行动
3. 需要再沟通的议题
4. 已安排但临近的场景
5. 领证/婚礼顺序与日期
6. 婚礼预算风险

用户不需要进入多个列表页面，才能知道当前卡点和下一步。

## 7. 关键业务规则

### 7.1 顺序规则

- 上门顺序可调，但两个上门节点都必须独立存在。
- 领证和婚礼顺序可调，两个节点都必须独立存在。
- 订婚可以跳过。
- 真实生活可以先发生后记录，系统提供补录能力，不把推荐顺序当成强制门禁。

### 7.2 事实与计划分离

- 计划日期表示“准备在哪天做”；实际日期表示“真实在哪天发生”。
- 修改计划不能覆盖实际日期。
- 用户把已完成节点改为进行中时，系统应保留变更记录或至少提示会影响当前进度。

### 7.3 共识与父母意见边界

- 父母意见可以记录，但不能被系统转换成“批准/拒绝婚姻”。
- “双方父母见面完成”只说明见面发生，不说明双方达成全部共识。
- “基本共识完成”应由用户逐项确认，不由系统根据父母态度猜测。

### 7.4 用户隐私与安全

- 所有婚姻进程、沟通记录、预算和花费只属于当前认证用户。
- 不要求录入父母身份证、联系方式等不必要的敏感信息。
- 备注、沟通记录和附件不能出现在公开页面、日志或错误信息中。

## 8. 异常与回退

| 情况 | 产品行为 |
| --- | --- |
| 男方上门完成，女方上门尚未完成 | 显示一次已完成、一次待安排；推荐下一步是完成另一方上门 |
| 两次上门顺序临时交换 | 更新未来顺序；保留已完成记录和原实际日期 |
| 父母见面后意见不一致 | 阶段标记“需再沟通”；保留分歧，不强制进入订婚 |
| 订婚不举行 | 标记“已跳过”，不产生逾期提醒 |
| 先领证后办婚礼 | 领证完成、婚礼进行中；首页不能提示“尚未结婚”而应显示“已领证，婚礼待完成” |
| 先办婚礼后领证 | 婚礼完成、领证进行中；仍需明确法律婚姻节点尚未完成 |
| 婚礼延期 | 修改婚礼计划日期，保留已完成行动项和历史；重新生成未来行动提醒 |
| 用户已经完成部分流程才使用模块 | 允许补录，不要求按推荐流程重做 |
| 预算超支 | 显示预算风险和差额，不自动取消任务或改变婚姻阶段 |

## 9. 一期范围

### 必须有

- 婚姻进程建档和当前阶段
- 两次上门独立节点及先后顺序调整
- 双方父母见面记录
- 基本共识议题记录
- 订婚完成/跳过
- 领证与婚礼独立节点及顺序调整
- 阶段行动项
- 婚礼预算与花费
- 首页下一步、风险和状态复盘
- 390px、768px、1280px 响应式布局

### 暂不纳入

- 情侣双账号和实时协作
- 父母独立登录、审批和投票
- 法律咨询、婚姻合法性判断或自动法律提醒
- 自动推断双方父母是否同意
- 供应商 CRM、合同管理、附件审查
- 宾客、桌位、请柬发送和座位排布的完整管理
- 日历同步、短信/微信通知、自动催办
- 婚后财务合并或家庭资产管理

## 10. 验收标准

| 编号 | 验收场景 | 通过标准 |
| --- | --- | --- |
| MAR-001 | 首次进入空数据 | 页面先询问当前婚姻阶段或允许创建进程，不展示泛化任务清单作为唯一入口 |
| MAR-002 | 调整两次上门顺序 | 切换“男方先/女方先”后，顺序标签和下一步提示同步；两次节点仍都存在 |
| MAR-003 | 只完成一次上门 | 页面明确另一方尚未完成；不把父母见面显示为已完成 |
| MAR-004 | 补录父母见面 | 即使推荐前置节点没有完整记录，用户可以补录，系统标记为用户补录而非自动推断 |
| MAR-005 | 记录共识分歧 | 能看到已达成共识和需再沟通议题；系统不显示父母审批结论 |
| MAR-006 | 跳过订婚 | 订婚显示“已跳过”，不出现在逾期或未完成统计中 |
| MAR-007 | 选择先领证后婚礼 | 两个节点分别显示，领证完成后页面显示“已领证，婚礼待完成” |
| MAR-008 | 选择先婚礼后领证 | 婚礼完成后仍显示“领证待完成”，不能把婚礼完成当作法律关系成立 |
| MAR-009 | 调整未来顺序和日期 | 未来计划更新，已完成节点的实际日期和历史不被覆盖 |
| MAR-010 | 两个节点都完成 | 首页显示“婚姻阶段已完成/进入婚后生活”，但保留历史和预算结算入口 |
| MAR-011 | 390px 浏览 | 阶段、顺序控制和操作按钮可读可点，无横向溢出；底部五项导航保持不变 |

## 11. 与现有嫁嫁嫁实现的重组建议

当前已有的预算、任务、花费、时间线和概览能力可以保留，但业务归属需要改变：

| 现有能力 | 重组后的归属 |
| --- | --- |
| 任务看板 | 阶段行动项；默认按当前阶段和负责人展示 |
| 时间线 | 婚姻节点时间线；区分计划日期和实际日期 |
| 预算与花费 | 婚礼执行阶段；从首页的主线指标降为风险支撑 |
| 任务状态 | 增加阶段语义，不能只用待办/进行中/完成表达父母见面和共识 |
| 婚期倒计时 | 改为婚礼节点倒计时；领证日期独立显示，不混成一个婚期 |
| 分类统计 | 继续服务婚礼预算，但分类应允许映射到婚礼行动项/阶段 |
